## 1. Schema Conflicts

### 1.1 merchant_name Column Discrepancy

**Conflict:**
- Migration `0001_unified-migration-fixed.sql` creates `merchant_name` column in `unified_files`
- Migration `0019_drop_merchant_name.sql` removes this column
- CLAUDE.md explicitly states: "**merchant_name DOES NOT EXIST** in `unified_files` table"

**Resolution:**
- Current schema does NOT have `merchant_name` in `unified_files`
- Company name must be obtained via JOIN: `companies.name` through `company_id` FK
- **Decision:** SoT 40_DATA_MODEL.md must NOT include `merchant_name` in `unified_files`

### 1.2 SoT 40_DATA_MODEL.md vs Actual Schema

**Conflict:**
- `40_DATA_MODEL.md` lists hypothetical/placeholder columns
- Actual schema defined in `database/migrations/*.sql` differs significantly

**Examples:**
- SoT mentions `processing_status` column - actual column is `ai_status`
- SoT mentions `receipt_id` in proposals - actual column is `receipt_id`
- SoT is missing many columns present in actual schema

**Resolution:**
- **Decision:** 40_DATA_MODEL.md must be completely rebuilt from migrations
- Canonical source: `database/migrations/*.sql`
- Per `MIND_SCHEMA_SOURCE_OF_TRUTH.md`: migrations are the single source of truth

## 2. Status Definition Conflicts

### 2.1 Processing Status vs AI Status

**Conflict:**
- `30_STATUS_MODEL.md` uses term `processing_status`
- Actual column name in code is `ai_status` (per `status_constants.py`)
- `MIND_STATUS_DEFINITIONS.md` correctly uses `ai_status`

**Resolution:**
- **Decision:** Use `ai_status` as the canonical term
- Update 30_STATUS_MODEL.md to reflect actual column name

### 2.2 Status Value Differences

**Conflict:**
- `30_STATUS_MODEL.md` lists illustrative values: `imported`, `queued_for_ocr`, `ocr_in_progress`, etc.
- `MIND_STATUS_DEFINITIONS.md` and `STATUS_MODEL.md` list actual values: `uploaded`, `processing`, `ocr_done`, `ocr_failed`, `manual_review`, `completed`, `failed`

**Resolution:**
- **Decision:** Use actual values from `status_constants.py`:
  - `uploaded` (not `imported`)
  - `processing` (not `queued_for_ocr` or `ocr_in_progress`)
  - `ocr_done`
  - `ocr_failed`
  - `manual_review`
  - `completed`
  - `failed`

### 2.3 Workflow Stage Status vs AI Status

**Conflict:**
- Some docs conflate `unified_files.ai_status` with `workflow_stage_runs.status`
- These are different fields with different purposes

**Resolution:**
- **Decision:** Clearly distinguish in 30_STATUS_MODEL.md:
  - `unified_files.ai_status`: Overall file processing state
  - `workflow_runs.status`: Workflow execution state (`queued|running|succeeded|failed|canceled`)
  - `workflow_stage_runs.status`: Individual stage state (`queued|running|succeeded|failed|skipped`)

## 5. Naming Inconsistencies

### 5.1 Workflow Type Names

**Conflict:**
- Code uses: `WF1_RECEIPT`, `WF2_PDF_SPLIT`, `WF3_FIRSTCARD_INVOICE`
- Some docs use: `receipt`, `creditcard_invoice`, `pdf_split`
- `unified_files.workflow_type` column: `receipt`, `creditcard_invoice`

**Resolution:**
- **Decision:** Document both forms:
  - Workflow key (in workflow_runs): `WF1_RECEIPT`, `WF2_PDF_SPLIT`, `WF3_FIRSTCARD_INVOICE`
  - Workflow type (in unified_files): `receipt`, `creditcard_invoice`

### 5.2 AI Stage Names

**Conflict:**
- Original design: AI1, AI2, AI3, AI4, AI5, AI6, AI7
- Actual implementation: `detect_type` (AI1), `r_ai3` (AI3), `r_ai4` (AI4), `ai5` (AI5), `fc_parse` (AI6)

**Resolution:**
- **Decision:** Document mapping in 70_AI_PROMPTS_AND_ROLES.md:
  - AI1 = `detect_type` (Document Type Classification)
  - AI2 = Expense classification (may not be active)
  - AI3 = `r_ai3` (Data Extraction)
  - AI4 = `r_ai4` (Accounting Classification)
  - AI5 = `ai5` (Credit Card Matching)
  - AI6 = `fc_parse` (FirstCard Invoice Parsing)
  - AI7 = Box Enrichment (planned)
